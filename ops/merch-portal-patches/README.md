# Патч QR-портала мерчендайзинга

`merch-portal-mount.patch` — минимальные изменения исходников отдельного портала на сервере мерчендайзинга, **не** копия его приложения. Исходники `/opt/pharmacy-crm-demo` на момент аудита 2026-09-23 не были Git-репозиторием. Патч проверен на изолированной копии и применён к production при релизе ePharm v0.1.10; прежние source и `dist` сохранены для отката.

`strip-demo-autofill.mjs` — отдельный fail-closed sanitizer для исходного `src/Auth.jsx` с проверкой SHA-256. Он извлекает демонстрационные credentials **только в память**, удаляет автоподстановку без помещения старых строк в Git diff, собирает приложение и проверяет, что исходные значения отсутствуют в новых JS assets. Это не отзывает существующие учётные записи: по явному решению пользователя их сохраняют активными для тестирования в данном rollout, принимая риск их публичности. Старые бандлы и их резервные копии не следует публиковать сверх уже доступных маршрутов.

## Что исправляет

- Один Vite build загружает CSS/JS как с прямого `/staff`, так и с опубликованного ePharm `/merch/staff`.
- QR-страница `/merch/staff` открывает именно публичный портал заданий и отправляет запросы в `/merch/api/...`; прямой dev URL продолжает использовать `/api/...`.
- Фотоотчёты и эталон `/pharmacy-shelf.png` загружаются через соответствующий `/merch/` префикс. Переход к другому заданию сохраняет этот префикс.
- Восстановлен отсутствующий `src/catalogCities.js`: текущий исходный `PlacementPlanWorkspace.jsx` импортирует его, без него `npm run build` падает. Реализация перенесена из уже обслуживаемого на сервере JS-бандла `index-CuCqW6Jl.js` (SHA-256 `96bf8409e18298a65d1cb98bc26c72c89414f97fee9b3a4983289049bfdd5aed`), а не заменена заглушкой. Тест фиксирует набор из десяти значений «город требует уточнения» и алиасы Усть-Каменогорска.

Если хотя бы один SHA отличается, перепроверить diff; патч нельзя накатывать вслепую. Сначала нужен независимый backup изменяемых исходников и план сохранения текущего `dist`. В **отдельной staging-копии**, не в `/opt/pharmacy-crm-demo`, порядок такой: `git apply --check` → применение patch → перенос включённого lockfile в корень копии → `npm ci` → sanitizer `--check` и `--apply-and-build` → Node-тесты и browser smoke. `strip-demo-autofill.mjs` прямо запрещает запуск с live-root. Создание отдельного Git-репозитория для исходников мерча — отдельная задача; этот patch bundle не должен становиться заменой контроля версий.

Проверенные команды в изолированной копии: sanitizer `--check`, sanitizer `--apply-and-build`, `node --test scripts/test_catalog_cities_recovery.mjs scripts/test_public_merch_mount.mjs scripts/test_public_merch_build.mjs`; 6 из 6 тестов прошли. Sanitizer проверил 25 новых JS assets. Сборка даёт только предупреждения Vite о chunk size и одном смешанном импорте.

В исходной поставке нет lockfile (`package-lock.json` и аналогов), поэтому первоначальная сборка через `npm install` не была воспроизводимой. В bundle включён сгенерированный на изолированной копии `package-lock.json` (его нужно положить в корень merch source после применения patch). Пакет `vite` намеренно обновлён с `6.4.1` до `6.4.3`: прежний lock давал один HIGH advisory для Vite dev server, новый `npm audit --audit-level=low` — 0 уязвимостей. Это уязвимость инструмента разработки, а не доказанный путь эксплуатации уже собранного Python-served `dist`. На новом lock `npm ci`, `npm run build` и 6 тестов прошли.

## Выпуск `dist` без потери фотографий

Live `dist` — это не только Vite build: кроме `assets` там три sidecar-каталога, которых нет в `public/` и которые новая сборка удалит. На аудите 2026-09-23: `pharmacy-exteriors` — 1 037 файлов / 187 793 317 байт, `pharmacy-exteriors-web` — 111 / 7 815 264, `catalog-previews` — 26 / 19 848 231. Все 1 174 файла обычные, без symlink, владелец `pharmacy-crm:pharmacy-crm`. Семь root PNG в новой сборке имеют те же SHA-256, что live. Старый `assets` содержит 34 hash-named файла; их временно сохраняют для уже открытых вкладок и динамических импортов. Старый JS содержит опубликованные demo credentials, которые пользователь решил пока не менять: новые бандлы будут очищены, но нельзя заявлять, что старые значения исчезли из публичного доступа.

Проверяемый порядок для релизного кандидата:

1. Проверить SHA базовой версии, свободное место и HTTPS. Сейчас единственный постоянный mount — ext4 `/`, свободно примерно 1,68 ГБ (98% занято); **не** создавать ещё одну полную копию всех backup. Выполнить сборку на изолированной машине, передать на сервер только проверенный новый `dist` (около 16 МБ) и малые patched source/lock в staging, не выполнять `npm ci` внутри live-каталога.
2. Создать candidate `dist` рядом с live на том же ext4 и до любого переключения выполнить `node preserve-dist-sidecars.mjs --prepare <live-dist> <candidate-dist>`. Скрипт ничего не пишет в live: копирует три sidecar-папки и старые hash-named assets только в candidate, отказывает при symlink, неожиданном root-файле, отличии семи PNG, битых относительных JS/CSS, изменении source во время копии или остатке менее 512 МиБ. Он сравнивает count, суммарный размер и SHA-256 **каждого** файла через digest полного path-manifest. Повторить `--verify` после установки владельца `pharmacy-crm:pharmacy-crm`; сохранить вывод manifest и контрольные SHA трёх публичных sample URL из preflight.
3. Зафиксировать явное решение пользователя оставить три demo-учётки активными для тестирования и принять связанный риск; в рамках данного rollout не менять их. Затем отдельно проверить `exchange-dist.py`: live basename обязан быть `dist`, candidate — `dist.candidate-<release-id>`, оба — реальные соседние каталоги одного project root и filesystem. Project root должен содержать `scripts/api_server.py` и `package.json`; оба `index.html` сверяются с **явно переданными** SHA-256. Сначала вызвать `--dry-run` с путями и SHA старого/нового `index.html`; он хеширует каждый файл обоих `dist` и возвращает `plan_sha256`, ничего не меняя. Лишь после review плана вызвать `--exchange --plan-sha256 <точное значение>` с теми же аргументами. Любой drift отменяет операцию. Linux `renameat2(RENAME_EXCHANGE)` атомарно меняет каталоги местами на одном ext4; бывший live становится rollback-копией без дополнительного расхода диска. Двухшаговый `mv` не является атомарным и здесь не равнозначен. Bundle сам helper **не запускает**.
4. Сразу проверить HTTPS health, `/staff` и ePharm `/merch/staff`, новые JS/CSS, три media sample URL, их SHA-256, отсутствие console errors и изоляцию admin API. При провале — вызвать новый `--dry-run --rollback` с прежними путями и SHA старого/нового index, затем `--exchange --rollback --plan-sha256 <новый plan>`; это обратный атомарный обмен с проверкой, что live действительно содержит новую версию, а candidate — старую. После него восстановить изменённые source-файлы из малого backup. Не удалять rollback-копию и старые hash-assets до завершения оговорённого окна совместимости и отдельного решения о retention.

Локальный тест `node --test ops/merch-portal-patches/test-preserve-dist-sidecars.mjs` проверяет успешную копию/verify, отказ при порче байтов, symlink и отличии root PNG. Linux-only `python3 ops/merch-portal-patches/test-exchange-dist.py -v` проверяет dry-run → exchange → reverse rollback, повторное применение старого плана, drift, symlink, вложенный путь и неправильный marker. Оба теста работают только в синтетических временных каталогах, без production. Настоящее содержимое media-папок в Git не входит. Это сохранение статических данных, а не разрешение публиковать весь merch CRM через ePharm: Caddy должен оставаться deny-by-default.

## Зависимости для rollout

Сам по себе SPA-патч недостаточен. ePharm Caddy публикует **только** `/merch/staff`, нужные `/merch/assets/*`, `/merch/pharmacy-shelf.png`, фото через `/merch/api/task-files/*` и необходимые `POST /merch/api/public/task-dispatch*`; остальные CRM/API маршруты закрыты. Server key ротирован и передаётся к merch через проверяемый HTTPS `:8443`; прямой публичный HTTP 8080 закрыт. Проверки QR с действительным token нужно проводить в браузере телефона по мобильной сети: HTML, JS/CSS, эталон, чтение задания, загрузка фото, отправка, истёкший token. Не проводить mutating smoke-тесты с реальным production-заданием без согласования.

## Резервное копирование merch CRM

На production 2026-09-23 обнаружено, что `pharmacy-crm-backup.service` не запускался из-за неисполняемого `scripts/backup.sh`. После исправления этого препятствия обнаружилась вторая причина: роль приложения не имеет `SELECT` на новых таблицах и не может создать полный дамп. Drop-in `systemd/pharmacy-crm-backup.service.d/10-safe-backup-path.conf` запускает существующий script под системным `postgres` с peer-аутентификацией к PostgreSQL и дополнительной группой `pharmacy-crm` только для чтения uploads. Он не загружает общий env приложения с ключами: для backup заданы лишь необходимые несекретные параметры. Автоматические архивы пишутся в отдельный `BACKUP_DIR=/var/backups/pharmacy-crm-demo/scheduled`, владелец `postgres`, режим `0700`; родитель остаётся `postgres:postgres` и `0750`. Так 14-дневная ротация не затрагивает исторические и ручные архивы. Перед включением проверять права, `systemd-analyze verify`, достаточное место, успешный запуск oneshot, наличие архива и его SHA-256; старые архивы не удалять.
