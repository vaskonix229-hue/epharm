# Интернет-заказы: витрина -> Epharm -> касса

Статус: транспорт АСС → Epharm включён 2026-09-22 с явной границей времени и allowlist аптек.
До прохождения нового сквозного заказа на двух кассах одной аптеки функция не считается
принятой для промышленной выдачи; карточные заказы отдельно заблокированы до доверенного
серверного подтверждения оплаты.

## Границы решения

- Витрина сохраняет заказ и `epharm.order.created` в одном PostgreSQL transaction.
- Worker доставляет замороженное JSON-тело в Epharm с HMAC-подписью и повторяет
  временные ошибки с backoff. Старые заказы исключаются обязательной датой старта.
- Epharm идемпотентно принимает заказ, сопоставляет внешний филиал с аптекой и
  хранит историю переходов статуса.
- POSM получает только заказы своей аптеки по отдельному device token, показывает
  очередь фармацевту и может начать сборку, отметить готовность, выдать или отменить.
- Локальный offline-кэш очереди привязан к паре `pharmacyId` + `deviceId`. Старый кэш без
  такой привязки и кэш другой пары не показываются; после успешного опроса сервера
  кэш заполняется заново. Офлайн-действия с заказами запрещены.
- Worker читает изменения по монотонному cursor и переносит статус обратно в витрину.
- Телефон, имя, email, адрес покупателя и другие PII через этот контракт не передаются.

Мерчендайзинг и складская автоматизация не входят в контракт заказов и проверяются отдельно.

## Контракт и состояния

Входящий заказ содержит `eventId`, `orderId`, номер, внешний ID аптеки, время,
итог, валюту KZT, способ доставки/оплаты, состояние оплаты, признак demo,
шестизначный код выдачи и до 200 строк товара. Цена строки может отсутствовать,
если исходная система ее не отдала; отрицательная или неточная цена отклоняется.

Допустимые переходы:

```text
submitted -> assembling -> ready -> completed
     |            |          |
     +------------+----------+-> cancelled
```

- Каждый action передает `expectedVersion`; гонка двух касс возвращает `409`.
- Выдача требует точный шестизначный `code`.
- После пяти неверных попыток ввод блокируется на 15 минут.
- Наличный заказ требует явного `cashCollected=true`.
- Карточный заказ выдается только при доверенном `paymentStatus=paid`.
- Отмена требует причины и подтверждения в интерфейсе.
- Не назначенный заказ нельзя обрабатывать; неактивная аптека не может продолжить
  сборку или выдачу. HQ сохраняет возможность отменить такой заказ.

## Безопасность

- Витрина подписывает `timestamp + method + path/query + SHA-256(body)` общим
  секретом длиной не менее 32 байт. Окно времени по умолчанию 300 секунд.
- Код выдачи в Epharm хранится только как HMAC, привязанный к `orderId`; открытого
  кода в БД Epharm нет, одинаковые коды разных заказов не коррелируют.
- POSM token генерируется отдельно для пары `(pharmacyId, deviceId)`, в backend
  хранится только SHA-256, на Windows token защищается DPAPI CurrentUser.
- Нормальный enrollment — предварительная выдача HQ одноразового token для одобренной пары
  `(pharmacyId, deviceId)`. Регистрация по legacy `POSM_DEVICE_KEY` закрыта по умолчанию и
  остаётся только для короткого контролируемого переходного окна.
- Администрирование доступно только `SYSTEM_ADMIN` и `HQ_HEAD`.
- Production-секреты не входят в Git, image, ZIP POSM или логи.

Оставшийся rollout-риск: старые кассы могут всё ещё содержать общий legacy key. Перед массовым
включением каждой кассе выдают индивидуальный token через HQ, проверяют scope и отзыв, после чего
fleet-key удаляют из локальной конфигурации.

## Переменные Epharm

```dotenv
FULFILLMENT_ENABLED=false
FULFILLMENT_SHARED_SECRET=<random-48-byte-base64>
FULFILLMENT_SIGNATURE_SKEW_SECONDS=300
FULFILLMENT_DEVICE_REGISTRATION_ENABLED=false
FULFILLMENT_TRUSTED_CARD_PAYMENT_AUTHORITIES=
```

`FULFILLMENT_ENABLED=false` оставляет admin read/mapping доступными, но закрывает
прием заказов, feed, кассовую аутентификацию и изменение статусов.

## Переменные витрины

```dotenv
EPHARM_ORDER_SYNC_ENABLED=false
EPHARM_BASE_URL=<trusted-epharm-api-base>
EPHARM_FULFILLMENT_SHARED_SECRET=<same-secret-as-epharm>
EPHARM_ORDER_START_AT=<explicit-UTC-cutover-time>
EPHARM_ALLOW_PRIVATE_HTTP=false
EPHARM_SYNC_POLL_SEC=10
EPHARM_SYNC_TIMEOUT_MS=15000
EPHARM_SYNC_BATCH_SIZE=20
```

Если связь возможна только по приватному `http://...:8060`, исключение
`EPHARM_ALLOW_PRIVATE_HTTP=true` разрешается временно и документируется. Публичный
HTTP запрещен. Старые строки outbox до `EPHARM_ORDER_START_AT` не отправляются.

## Безопасный rollout

1. Снять backup БД, env, compose и текущих image IDs на обоих серверах.
2. Развернуть миграции и код при обоих flags `false`; проверить health и admin read.
3. Заполнить точные pharmacy links по стабильным ID, не по названию/нечеткому поиску.
4. Включить worker при выключенном backend feature нельзя: сначала согласовать
   единое время включения и убедиться, что `EPHARM_ORDER_START_AT` задано.
5. Через HQ предварительно выдать tokens двум одобренным кассам одной аптеки; legacy enrollment
   не открывать. Проверить scope и отзыв каждого token.
6. Провести пилот только на cash/demo или с подтвержденным trusted paid source.
7. После приемки отдельно расширять список аптек. Массовое включение запрещено.

Откат: сначала выключить worker на витрине, затем `FULFILLMENT_ENABLED=false` в
Epharm. Миграции и накопленные записи не удалять. POSM продолжает основной экран,
рекомендации и продажи независимо от модуля заказов.

## Приемка

Обязательные проверки перед промышленным включением:

- атомарность order + outbox и идемпотентный повтор того же event;
- отклонение измененного тела с тем же event/order ID;
- строгий JSON, HMAC, просроченная подпись и отсутствие PII;
- неизвестная/неактивная аптека и ручное назначение;
- очередь более 50 заказов и update feed более 200 событий;
- две кассы одновременно меняют одну версию заказа;
- все разрешенные и запрещенные переходы статусов;
- пять неверных кодов, lock и успешная выдача после разблокировки;
- cash confirmation, unpaid card rejection и demo policy;
- offline/restart worker, lease recovery и сохранение последнего customer snapshot;
- отзыв device token и недоступность чужой аптеки;
- rollback flags без влияния на POSM-рекомендации и клиентский экран.

Положительный локальный test suite подтверждает реализацию, но не заменяет эти
сценарии на реальной витрине и двух кассах пилотной аптеки.
